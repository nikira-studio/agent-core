# Changelog

Notable changes to Agent Core are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versions follow [Semantic Versioning](https://semver.org/).

## [1.3.0] - 2026-11-13

The release that makes Agent Core run itself: nothing it promises depends on an agent remembering, and a person's role is setup and exceptions.

**Upgrading from 1.2.x.** Take a backup first. The schema migrates itself on start (revisions 24 to 27: a credential request remembers its task; any Memory Clean-up suggestion still pending is closed as rejected; two unused settings and the unused `can_delegate` column go; a connection check can note that it cannot be tested; nothing else in your data changes). The session context now arrives with an agent's first call of any tool, so agents that never call `session_context` still start informed; expiring and automatic retractions are restorable. Removed surfaces answer old clients with a clear error instead of a 404: the REST routes under `/api/memory/proposals` answer `410 REMOVED`, and the MCP tools `memory_pin` and `memory_pinned` answer `TOOL_REMOVED` with what to do instead. A `memory_suggestions` key is no longer in `attention_list`, and `workspace_sync` no longer returns `pinned`.

### Added

- **The session context comes to the agent.** The first MCP call an agent makes after a quiet hour (`AGENT_CORE_SESSION_CONTEXT_IDLE_MINUTES`, default 60, 0 turns it off), whichever tool it is, returns the session context beside its normal answer, with the `execution_id` to use. The Claude Code hook stays; the generated instructions and the MCP server instructions now say plainly to call `session_context` first. The index line no longer reads "0 of 2 active".
- **Answer a question where it is asked.** A question an agent asked a person is answered on **Needs you** with a text box and **Send answer**; the agent's next session shows the question, the answer and that it is resolved (a lapsed question shows as lapsed, and the Activity row says so). Each row says which task and workspace it is about, which agent asked and how long ago, what sending an answer does (it goes to that agent the next time it works in the workspace, and the ask closes), and the button reads **Mark as dealt with** until something is typed. An ask can carry `needs_human_url` (where the person acts, in another system): the row then leads with **Open in <that site>** and the answer box is secondary. **See the task and its notes** opens the task on the Activity page.
- **Keyword search finds inflected words.** With no embedding backend, "invoice export" finds "Invoice exports use ..." and "csv delimiter" finds "delimited CSV": when the exact words match nothing the search tries word stems, then any of them.
- **A first run starts with a workspace.** Getting started, the README and the quickstart create a workspace first; an agent created with defaults in an install with one workspace works in it (so two such agents share it), Create Agent shows "Which workspace will it work in?" in the open (the separate read and write ticks are under Advanced access), and Connect preselects the only workspace and shows **Generate One-Time Key** before the config it fills.

### Removed

- **The Memory Clean-up queue.** There is no queue, no card on the Memory page, no Overview line, no review settings (unconfirmed-fact age and importance, scheduled scan), no "never confirmed" or pinned badges, and no `memory_suggestions` in `attention_list`. Whether a memory is useful is not a question a person is asked.
- **Assigning work to agents.** `activity_pickup`, **+ Assign a task** and **Reassign** on the Activity page, the `reassign_to_agent` recovery action, creating an activity for another agent with `assigned_agent_id` on `POST /api/activity`, and the inbound `activity.assign` command are gone: in five months nothing was ever assigned to an agent. Agents open and close their own tasks; hand work over with a handoff. `activity.create` through the inbound webhook still creates a task for the named agent, which sees it in its session context. `POST /api/activity/pickup` and the `assigned_agent_id` create answer `410 REMOVED`; `activity_pickup` answers `TOOL_REMOVED`.
- **`memory_feedback` and its counts** (they nudged ranking and had been used 37 times in five months), **`min_confidence`** from the MCP schema and the dashboard (REST and old MCP clients may still send it; it is ignored) and **confidence** from the dashboard forms, **host anchors being checked** (a `host:` anchor stays as a plain label, and no longer uses a place in the verification pass), the **end-execution call** (`POST /api/workspace-sync/end` answers `410`) and the **ended/stale execution states**, and three leftovers nothing read: the `solo_mode_enabled` and `installed_version` settings rows and the `agents.can_delegate` column (schema revision 26).
- **Pinned standing context.** `memory_pin`, `memory_pinned`, the pinned section of `workspace_sync` and of the session context, and pin requests are gone (none had ever been used). The session context lists the key records of a workspace; write a decision with `memory_write`.

### Changed

- **Three plain cases are refused when an agent writes memory.** A bare log of one occurrence (a heartbeat, a tick, an idle run) and bare ticket-closeout narration are refused with `TOO_SPECIFIC_TO_ONE_OCCURRENCE` and a pointer to `activity_update`; "bare" means no more than a few ordinary words follow the status, so a fact that opens with a closeout, or a log line that goes on to state something lasting, is saved (and the hourly clean-up leaves it alone). A text that is the same statement as an active record in the same workspace (not merely alike at the start, and never when a number, identifier, path or name differs) is refused with `DUPLICATE_OF`. A correction that reads almost the same as an active record but differs in its details is saved with a `SIMILAR_ACTIVE_RECORD` warning naming the record to pass as `supersedes_id`. Refusals are audited (`memory_write_refused`); a person saving a memory in the dashboard is never refused.
- **Six entries in two groups.** The sidebar is *Handle exceptions* (Needs you, Activity, Memory) and *Set up* (Agents, Services, Settings); the other pages are tabs inside their entry (Agents: Connect, Workspaces; Services: Credentials; Settings: Users, Webhooks; Activity: Audit log; Needs you: Approvals). Every old address still works. On a phone the navigation is behind a Menu button.
- **Needs you.** The home page is called Needs you; an empty list says there is nothing to do, and a credential request is answered right in its row (type the value, Save). Task rows on the Activity page open to the result, the latest note, next steps and open questions. After you register you land on the home page, and turning on two-step sign-in is an optional Getting-started item instead of a forced step. A failed access check on the Connect page has a **Give access** button.
- **Needs you holds only what a person can still act on.** Closing a task (completed or cancelled, by its agent, an admin or a cancel from the dashboard) ends the ask it carried, and so does the 48-hour abandoned close; an ask nothing has touched for 7 days (`AGENT_CORE_ASK_EXPIRES_AFTER_DAYS`) lapses; a `needs_human` that says no action is needed is kept as an open question instead of being raised. A blocked task with nothing waiting on a person also ends after the same 7 days, as cancelled "Ended without report". The closer's response lists what was ended.
- **An agent with no workspace has a working session start.** `session_context` (MCP and `POST /api/session-context`) also serves the agent's own private scope, and picks it when the agent has no workspace: its own unfinished tasks, recent results and key memories, plus an `execution_id` for its writes. Another agent's private scope is still refused. `workspace_sync` stays workspace-only.
- **Generated agent instructions are about 300 words, not 2,000.** CLAUDE.md, AGENTS.md and the session prompts now say only what is specific to the workspace (its scopes, the session rhythm, how to close a task, when a memory is worth writing and when not, secrets) and rely on the MCP server's own instructions and tool descriptions for the rest. No tool catalogue, no class tutorial, no sync mechanics. The Stop hook's request when a session ends with a task still open now asks for a one-or-two-sentence `task_result` saying what was done and where, not the last message. Regenerate and replace an older CLAUDE.md or AGENTS.md from the Connect page; the old text still works but names tools that were removed.
- **Plain noise retracts itself.** Per-occurrence logs, ticket-closeout narration and duplicates (the newest is kept) retract at the hourly maintenance run, and a fact whose anchor is definitively gone in two checks at least an hour apart retracts too. Each retraction is soft and restorable for the retention period, audited as `memory_auto_retracted` with the rule as the actor, and a run retracts at most 20 records. The suggestion rules for stale and unconfirmed facts are switched off: Core does not retract on age or on a judgement about usefulness.
- **Tasks that stop close themselves.** An open task with no update for 48 hours (`AGENT_CORE_ABANDONED_AFTER_HOURS`, 0 turns it off) is closed as cancelled with the result "Ended without report", ending at its last sign of life; an agent that comes back starts a new record. The Overview no longer lists stalled tasks, the Activity page has no Stale tab, and a blocked task with no question for a person is not a chore. Nothing is left to clear.
- **One row per agent request.** A credential request remembers the task its agent was on (schema revision 24). The person sees the request once, not the request and the blocked task, and providing the credential marks that task's ask answered.
- **Parallel sessions keep their own records.** A session that passes its `execution_id` updates the record its execution started; a record no live session owns is taken over, and one another live session is working on is left alone. Two sessions sharing one agent key used to overwrite each other's description and notes. Any write that carries an `execution_id` now counts as the session being alive.
- **Completing a task needs a result.** `activity_update` with `status: completed` (and the REST call) is refused without a `task_result`, so a finished task always says what was done and where. Almost every agent already sent one.
- **History keeps its dates.** Closing a blocked record later no longer moves its end to the day it was closed, so an old record closed in a clean-up is not shown as that day's work; the session context says "(closed out <date>)" when the two differ.
- **Maintenance buttons are under Advanced.** Run Maintenance and Re-embed (Settings) and Prune Log (Audit) sit behind an Advanced fold, and the Workspace synchronization panel is gone from the Activity page. Maintenance runs by itself every hour.
- **LifeQuery and HealthQuery ready-made services** are listed with the other built-in services, as in 1.2.1, now version 1.0.1: plain descriptions ("connection", "service address", the allowed private addresses list), read-only effect declared on every action, and a read-only test action. An install made from the earlier copy is offered **Update**.


### Fixed

- **One origin chip on every Services card.** The card chip means one thing: "Built-in" (ships with Agent Core) or "Added here" (an imported MCP server or API spec, a web service, an adapter added to this install). The "Installed" chip is gone (every card is installed), and how a service talks (MCP server, API spec, HTTP) moved to the meta line. "Update available" and the health chip stay. The ready-made services pages say the same words instead of System / Local.
- **Activity > Tasks rows stay a line or two.** A task's title opens the full record in the shared detail dialog (also from a Detail button): facts (status, agent, workspace in plain words, started, last update, task link), then Result, Latest note, Next steps, Open questions and Needs you (with its answer box, or "Open in <site>"), each only when present, and the row's actions in the footer. The inline fold that poured text into one narrow column is gone; a task's actions show only the ones that apply; the Workspace column says "private to IT Admin" or the workspace's name instead of a raw scope. On Needs you, "Or tell <agent> here" is no longer folded.
- **Getting started shrinks when you are set up.** While a required step (workspace, agent, connect its tool, watch it work) is undone it is an open card, below anything waiting on you. Once they are done it is one quiet line at the bottom ("Getting started: set up · 1 optional step left") that opens the list, with Hide this (kept per user; Settings > Account, "Show getting started", brings it back); when every step is done it disappears. "Give it a service" now counts any enabled connection instead of never being done.
- **The Health strip says states, not instructions.** Tiles read "open to any program with its key", "blocked unless allowed", "report only: 3 would be blocked", each tile links to its setting, the two limits you chose sit under a small "Limits you set" label and are quieter than the four live tiles, text is centred, and Services says "all working" only when every enabled connection's last check passed or could not be run ("not checked yet" when none has been checked).
- **Memory detail shows only what exists.** No fold and no "not set" rows: the key (as "Replaces earlier notes filed under"), True from and True until, Last confirmed and the checked-against line each appear only when there is something to show.
- **A saved secret says it exists.** The vector search API key, a credential's value, a user's password and a webhook's signing secret show "A key / value / password / secret is saved" (with when it was saved where that is known) and a placeholder "•••••••• saved; type to replace", or "No key saved" when nothing is stored; the Local credential helper card says whether its key exists. The value is never rendered.
- **Fewer fold-outs.** A fold is kept only for long, rarely needed content (a whole form, a code sample, a list). One to three lines of help are shown as normal hint text, and no fold sits inside another: the re-embed section and its note are always visible, the memory dialog's optional fields are one fold, a memory's optional facts show only when set, the audit "Advanced" menu with one item is a plain Prune log button, and the one-time key explanation is a paragraph. A fold that remains is a quiet text toggle, not a full-width outlined box.
- **Retention shows its number.** "Kept for the retention period" now reads "kept for 30 days, then deleted for good" with the live setting (linked to the field for an admin), the retract confirmation says how long it can be restored, a retracted memory's detail says when it will be deleted for good, and the scratchpad hint names its days.
- **Adapter update backups clean themselves up.** An update used to leave the previous adapter folder (`.<id>.backup-<hex>`) in the data folder forever. Now only the newest one is kept for an installed adapter, the older ones are deleted when an adapter is installed or updated and in every maintenance run, an uninstalled adapter keeps none, and a half-made copy more than a day old is removed. The maintenance summary reports the count.
- **Services audit.** A passing connection check no longer hands back the start of the service's answer (it can be private: chat names, message ids). Removing an adapter whose shipped template was dropped in a later release keeps its installed copy (it was the only one, so deleting it made the adapter impossible to add again). The Firecrawl, Google Workspace, SearXNG, Securo, Transmission and WorldMonitor templates have new patch versions so an install made from an older copy shows **Update available** (the Transmission update restores the "at least one id" guard on remove/stop, Google Workspace gains mail attachments). Memory list and detail use the same words (Kind; "personal (the owner only)"), and "Written by" says it once.
- **One pop-up pattern everywhere.** Every dialog has a fixed header with a real title and a close X, a body that is the only thing that scrolls, and a fixed footer with the actions (the main one on the right). It opens centred and scrolled to the top with focus inside, closes on X, Escape or a click outside (a form with unsaved input asks before discarding), traps focus, returns focus to what opened it, and leaves the page behind still. At phone width it is a full-width sheet with header and footer still in view. The browser's own confirm, prompt and alert boxes are replaced by the same dialog; a delete names what it deletes. Memory detail now opens with the memory's topic as its title, the content first, a compact row of facts, how sure and where it came from in plain words, "More details" and "Earlier versions" collapsed (the version list never repeats the current content). The Check Health result is a wider dialog with the badge on one line.
- **Check Health tells the truth.** A connection check now ends one of three ways: passed, failed, or "Can't be tested" (the service has no read-only action to try, so it is checked when next used). "Can't be tested" is neutral: it is not red, not counted as an error or as "untested", and the summary counts it separately ("17 passed, 1 failed, 4 can't be tested"). The test picks its action in this order: the adapter's own `test_action`, the usual health names, then any other read-only action, and never one that needs input the connection doesn't have. A changed MCP tool list no longer reads "register a separate connector type": it says the tool list changed and what changed, and the service card (and the check result) offers **Update tool list**, which reads the list again through the connection's own credential, shows what was added, removed or changed, and saves only when you say so. The result lists who can use each connection in plain words, uses the right plural, and the card keeps a "Last check" line. New column `connector_bindings.last_test_note` (schema revision 27).
- **Settings > Security reads in plain words.** The encryption key row says what the key is and, when earlier keys are kept, why (and when the key last changed); the "Secrets Snapshot" is "How secrets are protected"; the key buttons and startup checks drop the jargon ("keyring", "primary", `sqlite_fts5`).
- **Old sign-ins clean themselves up.** The nightly maintenance run deletes sessions that have expired or sat idle past the limit (and half-finished sign-ins past their expiry), marks expired operator tokens as revoked at their expiry so they read like any revoked token, and deletes token rows older than the 13-month audit window. The run's summary reports the counts.
- **A wrong `execution_id` no longer loses a write.** `activity_update`, `memory_write`, the REST routes for tasks and memory, and approval proposals used to refuse the whole call when the id was unknown (for example one remembered from before a restart), belonged to another agent, or was for another scope. The write is now saved without that attribution and the response carries an `EXECUTION_ID_IGNORED` warning saying why. An id is never attributed to an execution the caller does not own. `workspace_sync` and its acknowledgement, where the id is the whole target, still refuse an unknown one.
- **Settings is one row of tabs.** Account, Memory, Data and backup, Security, Users and Webhooks sit in one row under the Settings heading (Users and Webhooks for admins), with no second level; `/users` and `/webhooks` keep their addresses. A row too wide for a phone scrolls sideways with a faded edge instead of wrapping into a second row. On every page with tabs (Needs you, Activity, Agents, Services, Settings) the heading comes first and the one row sits directly under it.
- **"More" on a row opens a floating menu.** On Agents, Activity and Services (connections) the menu sits over the page, anchored to the button and right-aligned, so the row keeps its width and height; it closes on an outside click, Escape or a choice, the arrow keys move through it, and it works at phone width.
- **Service cards never clip their buttons.** View Actions, Add Connection and Delete wrap onto a second line when the card is narrow instead of running off its left edge.
- **"Built-in" is only for services that ship with Agent Core.** A service made from an adapter someone added to this install's data folder is labelled "Added here".
- **Memory, Retracted tab: no header buttons.** Saving there would make an active memory and Search covers active ones, so both are hidden.
- **Deleting a credential tells the connections that used it.** Each one reads "Its credential was deleted; attach another" and its Test fails with that reason instead of passing; the delete confirmation names the connections and agents that use the credential first.
- **Deleting an agent also cancels what it left waiting on a person**: its pending credential requests close, and its session records go with it.
- **Actions on the Webhooks page say what happened.** Create, update and delete show a message, and messages now survive the page reload that follows an action. A test parses every page's script so a stray character cannot silence a page.
- **Add connection asks for the service address** where the service needs one, and says plainly when an address is a private one and where to allow it (Settings, Security, Allowed private addresses).
- **Plain words**: no "binding", "connector" or "Overview" on a page; webhook events read "A task starts" with a sentence, not an identifier; Delete buttons say Delete; two-step sign-in is named the same everywhere, and a wrong code says what to do; a restore says what came back and reloads the page; the Health tile says "Credential helper access".
- **Opening and closing a task in one call keeps everything.** `activity_update` with a description, a status and a result (and a handoff) used to create an active record with the result and the question dropped. It now stores all of it, refuses `completed` without a result before creating anything, and a different description while another task is open ends that task as "Ended without report" and starts a new one instead of silently renaming it.
- **A person's restore, write or confirmation is final.** No clean-up rule retracts a memory a person wrote, restored or confirmed, and a duplicate is the same statement: records that differ in a number, identifier, path or name are never duplicates. The audit entry and Detail name the record it was judged a duplicate of.
- **Shutdown takes under a second.** An open dashboard tab held the event stream open and the server waited for it, so every stop and deploy ran into Docker's ten second limit; streams now end when the server is told to stop.
- **An abandoned task keeps the time of its last update** instead of the time of the sweep that closed it, an uneventful verification pass writes no audit entry, a memory an owner saves through the API is no longer stamped as an agent's inference, and handoff fields accept text or a list for every field.
- **An ask that says nothing is needed no longer waits on a person.** "Nothing now" and "Nothing right now" join "No action needed" and "None" as texts that are not raised, and an older open ask with such a text is closed by the hourly run.
- **A retracted memory can be found, read and restored.** The Memory page has Active and Retracted views of the same table (same columns, workspace filter, paging and Detail); a retracted row has Restore where an active one has Retract, its State cell says when it was retracted and by whom or which rule, and its Detail view also gives the reason when one was given (`memory_retract` and `POST /api/memory/retract` keep the reason in the audit entry; `GET /api/memory/{id}` returns it as `retraction`).
- **Every automatic removal leaves a trace, and an expiry no longer destroys.** A memory whose `expires_at` passed is retracted (restorable for the retention period, every class, restoring clears the passed expiry) and the audit entry names it; the permanent deletion only happens to a retracted memory after the retention period, and that entry names each record too (id, topic, workspace, class; never the content).
- **The duplicate rule no longer retracts records that only open alike.** It compared the first 90 characters, so two decisions relayed in the same opening words were treated as one. Duplicates now need near-identical full text, a decision is never retracted by a rule, and a record under 24 hours old waits.
- **First-run and wording fixes from a new-user review.** The Verification Prompt is four steps (write, search, activity, report) in a scope the agent can write to, and uses the agent's private scope when no workspace is chosen (it used to ask for the person's user scope and be refused). A web service without a Base URL is refused when it is saved (a Base URL field on the form), and a new binding is tested as soon as it is created. The connection doctor no longer sends the dashboard cookie, so it can tell whether the endpoint really demands a bearer key. The agent-created dialog is no longer titled "New API Key" with no key in it. The shared-scope checkbox says what it does. Overview Health says "none set up" when there are no services. Credentials → Used by counts the agents that can already get a credential's reference. Scope pickers and lists show workspace and agent names instead of `workspace:` / `agent:` strings. Every page has `lang`, a `main` landmark and a skip link.
- **Docs that disagreed with the code.** Private addresses: a fresh install blocks them and an existing install allows them (`.env.example` no longer sets the older switch, which overrode that choice). Stale marking happens at the next hourly sweep or when a dashboard page lists tasks, so a quiet task can read active for up to an hour. Python 3.11 or 3.12; run uvicorn from the project folder. The README no longer says creating an agent shows its key.
- **The change feed names who made a change.** A memory a person retracted in the dashboard showed up in an agent's session context as "retracted by" the agent that had written it, and a blocked task a person closed showed "completed by" the agent that owned it, because the feed named the record's author. It now names the person or agent that did it for retract, restore, confirm, pin, supersede, and for closing, cancelling, reassigning or editing a task. Authorship of the record itself is unchanged.
- **A task that is being reported on no longer goes stale.** Only an empty heartbeat refreshed a task's heartbeat; a progress note, a result or a new description did not, so any task running longer than five minutes was marked stale however often it reported, and a stale task could not recover even from a real heartbeat. An update from the agent that owns the task now refreshes the heartbeat and brings a stale task back to active (and sends `activity_recovered`); an admin editing a task from the dashboard does not count as a sign of life. The REST heartbeat call on a stale task works instead of failing. The agent instructions no longer ask for a heartbeat every one to two minutes: a short progress note every few minutes is enough.
- **A failed service run keeps its reason.** When a service answered with a refusal (HTTP 404, 500 and the like) the run log held a failure with no message, no code and the category "unknown", so most failures could not be diagnosed. The log now keeps the HTTP status as the reason (`HTTP_404`, "The service answered HTTP 404"), sorts it into the usual categories (credential, rate limited, caller error, remote service), and says so plainly when a connector gave no reason. The response body still stays out of the log; only its size is kept, for failures as well as successes.
- **Services imported from an OpenAPI spec can be run.** The shared call passed a `session` keyword that the OpenAPI executor did not accept, so every action on such a service failed with "unexpected keyword argument 'session'" before it left Core. It is accepted and ignored now.

### Changed

- **Texts that promised more than the product does.** Memory Clean-up says what its numbers mean: *Answered* is a card that was answered and applied, and on a confirm card that includes retracting an out-of-date or not-worth-keeping memory (the guide and the column headings now say so; the audit entry `memory_proposal_decided` already carried the outcome). `workspace_sync_ack` says that an unacknowledged page is delivered again. Anchors are described as they work: a `repo:` anchor is checked only where the workspace is mapped to a directory (`workspace_repo_roots`, empty on a new install), a `host:` anchor only through a service binding for that host, and a check that finds the subject there changes nothing visible. The credential guides list service bindings and credential consumers before the local credential helper, which is only for a tool you run yourself. The agent instructions say pins are rare operator-granted standing rules and an empty result is normal.
- **A search of an empty scope says so.** `retrieval_mode` reported `fts_only` whenever there was nothing to compare by meaning, which read as a fault in the embedding backend. When no record in the scopes searched passes the filters it is now `no_candidates`; `fts_only` keeps meaning keywords only because the embedding step was off, failed or scored nothing. The `memory_search` audit entry also records the `scope` asked for, the scopes searched, how many records were `candidates`, what the `embedding` step did (`ok`, `not_used`, `unavailable` or the failure) and how many it `scored`. The quickstart no longer says a search always covers everything the agent can read (a narrower default recall set limits it).
- **`activity_pickup` is described as what it is.** It returns the agent's own oldest open task. Nobody assigns work to agents on most installs, and the Activity page has no "Assign Work" form (the README and integrations guide said it did). The text now says a task reaches an agent through **Reassign** on the Activity page, an admin's `POST /api/activity` with `assigned_agent_id`, or an inbound webhook. The generated CLAUDE.md, AGENTS.md and session prompts no longer send every session to call it at startup; the tool, the REST call and the Reassign button are unchanged.

## [1.2.1] - 2026-11-11

**Upgrading from 1.2.0.** Nothing to do beyond the usual: take a backup, pull and restart. The one database change (schema revision 23) is applied on start and only updates the built-in web service's default description. This release is mostly dashboard readability and wording, one list of what is waiting on a person, small fixes to the documentation and API errors, and the removal of two features nothing used (image export from service results, the Activity snapshot counters).

### Changed

- **On a phone**, the sidebar keeps its group headings (Work, Access, Capabilities, System) with the pages under each, instead of one wrapped cloud of buttons. The Agents list, the Services bindings and recent runs, and Overview's Recent Activity become one block per row, with the labels beside the values and the **Created** column left out, so row buttons are never off-screen. Agents and bindings show **Edit** and **Connect** (or **Edit** and **Test**) and put the rest, including Delete, under **More**, so Delete no longer sits next to Deactivate.
- Deciding an approval now says what happened ("Approved: <title>" or "Rejected: <title>") and the request page links back to **Waiting on you**.
- **Rotate Key** and **Rotate helper key** are amber, not red, and each opens a dialog that says what keeps working and what stops, in place of a browser confirm box.
- **Readability.** Filled buttons, the active page and write tags use a darker blue, and the red delete button a darker red, so their white text reads at 4.5:1 or better; muted text, links, error and warning text were adjusted so they meet the same level in the dark and light themes (a test now checks the colour pairs). The Secondary button no longer turns its text white on a light background when hovered. Small text is at least 12 px.
- The built-in web service is described as "A web service reached over HTTP with an API key" (an existing install's old default text is updated; text someone wrote is left alone, schema revision 23), and the remaining "connector type" wording in the Services page and its not-found message reads "service".

- Every dashboard page now has its headings in order: the page title is an h1, each card's title an h2, and a section inside a card an h3, so a screen reader or an outline no longer jumps from h1 to h3. The look is unchanged (the levels are styled by class, not chosen for size).
- **Overview** no longer shows the row of count tiles (users, agents, workspaces, open tasks, memories). They repeated what each page already shows; the page now reads Waiting on you, Health, Search and Recent Activity.

- Rotating the local credential helper key is now recorded in the audit log (`broker_credential_rotated`: who, when, and that the previous credential was retired; never the credential). A refused or failed encryption-key rotation or restore is recorded too (result `failure`, with the reason and never the key); successful ones were already recorded.

### Security

- Deciding an approval takes a dashboard sign-in. An operator token placed in the browser cookie used to be accepted by the decide route; it is now refused like any other non-browser credential.
- Key operations (credential key rotation, backup, restore, restoring a key) are now exclusive across worker processes as well as threads, through a lock file `.key-operation.lock` in the data directory. Before, with more than one worker (`AGENT_CORE_WORKERS` above 1), two workers rotating at the same moment could each add a new key to the same old list, and the second write dropped the first's key, leaving anything encrypted with it unreadable. A crashed worker cannot leave the lock held; a key operation that cannot get it within five minutes stops with an error instead of waiting forever. No action needed on upgrade; the empty lock file is created on first use and can be left out of backups.
- The batch health check (`POST /api/connector-types/health-check`, the Services page's **Check Health**) tests at most 25 bindings per request (the response says how many were `skipped`; the longest-untested bindings go first, so repeating the check reaches the rest; narrow with `scope` or `connector_type_id`) and needs the `connectors_execute` capability, like testing one binding. Before, one request could run every visible binding's test and write as many audit rows. **Upgrade note:** a read-only key that called it is denied.
- The local broker wrapper (`runner/agent_core_broker.py`) warns on stderr when its URL is plain `http://` to a host other than this machine, because the broker credential and the secrets it fetches would cross the network unencrypted; a private address or Docker network name still warns. It still runs. `AGENT_CORE_BROKER_PLAIN_HTTP=refuse` makes it stop, and `--allow-plain-http` (or `AGENT_CORE_BROKER_ALLOW_PLAIN_HTTP=1`) marks a link as trusted. URLs that are not `http://` or `https://` are refused. **Upgrade note:** an install that points the wrapper at another host over `http://` now sees the warning on each run; nothing else changes unless it opts in to `refuse`.
- With more than one worker (`AGENT_CORE_WORKERS` above 1), a credential key rotation in one worker now reaches the others: each notices the rewritten keyring file and reloads it, so none goes on encrypting with a key that is no longer the primary. No action needed; a single worker (the default) behaves as before.
- The one-time backup key is returned in the body of `POST /api/backup/export`, with a `download_path`; the encrypted file is fetched with `GET /api/backup/download/{id}` (once, by the same admin, within 10 minutes). It is no longer sent in the `X-Agent-Core-Backup-Key` header, which proxies and logs keep. **Upgrade note:** a script that exported a backup and read that header, or saved the response as the file, must now read `data.backup_key` and download from `data.download_path`; the dashboard's Export button is updated.
- Testing a service binding (`connectors_bindings_test`, and `POST /api/connector-bindings/{id}/test`) now needs the `connectors_execute` capability, because a test calls the real service with the stored credential. **Upgrade note:** a key that has only `connectors_read` and ran binding tests now gets `CAPABILITY_DENIED`; give it `connectors_execute` if it should keep testing. Listing and describing bindings still needs only `connectors_read`.
- A login session token is accepted as a Bearer key only on `/api/auth/*` (sign-in, identity, effective authority, logout), so apps that use Agent Core as their sign-in keep working. Everywhere else a person's session comes from the browser cookie. **Upgrade note:** a script that sends a person's session token (often a cookie pasted from the browser) to other routes gets `401 SESSION_BEARER_NOT_ALLOWED`; switch it to an operator token. Agents keep using their agent keys.
- Operator tokens: short-lived Bearer tokens (5 to 60 minutes) a signed-in person creates under **Settings → Operator Tokens**, or with `POST /api/auth/operator-tokens` from the browser session. Shown once, revocable (`GET`/`DELETE /api/auth/operator-tokens`), and requests made with one are recorded as that person. They replace pasting a session cookie into scripts that must act as a person, such as attended install scripts. An operator token or a Bearer login session cannot create operator tokens. Migration 17 adds `operator_tokens`.
- CSRF protection: a state-changing request authenticated by the session cookie must send `X-CSRF-Token`, which dashboard pages add to every request. Requests with an `Authorization` header are unaffected.
- Login sessions are signed with their own random key (`session.key` in the data directory) instead of the credential encryption key, and only that key is accepted. Before, a session token was signed with the credential key and every retired key still verified one. **Upgrade note:** every session ends once on upgrade, so people sign in again, including in apps that use Agent Core as their login. Rotating the credential key no longer affects sessions; deleting `session.key` and restarting signs everyone out.
- The key status in Settings shows a digest of the primary key instead of its first characters.
- The failed-login and failed-OTP rate limits are kept in the database (migration 16 adds `rate_limit_buckets`), so they hold across workers and restarts instead of being per process. Behind a reverse proxy, set `AGENT_CORE_TRUSTED_PROXIES`, or all clients share one per-address login bucket. Behind a trusted proxy the client address is read from `X-Forwarded-For` right to left, so a client can no longer escape the limit by sending its own header. `docs/troubleshooting.md` shows how to clear a lockout.
- `POST /api/dashboard/vector-settings` no longer returns the stored embedding API key in its response; it reports `vector_has_api_key` instead, as the settings page already did.
- The Generic HTTP connector only sends the binding's credential to the configured `base_url` host; a caller-supplied `url` on another host is refused. Adapter path parameters are percent-encoded as single segments, and only a manifest path that is literally absolute can replace `base_url`.
- Upstream response bodies are read with a 10 MB cap, so a runaway upstream cannot exhaust the process; a body over the cap is reported as `RESPONSE_TOO_LARGE` rather than parsed cut off.
- TOTP codes are single-use: a code that already signed in is refused for the rest of its window. Migration 15 adds `otp_secrets.last_used_step`.
- MCP `memory_verify` without a `scope` verifies only the caller's writable scopes instead of the whole installation.
- `credential_request` needs read access to the scope as well as write access, so a write-only key cannot learn which entries exist.
- The audit page escapes every cell, including a forwarded client address, and the audit CSV export neutralises spreadsheet formulas.

## [1.1.0] - 2026-10-28

### Added

- Credential requests: the MCP `credential_request(scope, name, purpose)` tool lets an agent ask for a secret it needs without the value passing through it. A person fills or declines the request under **Requested by agents** on the Credentials page (`GET /api/credentials/requests`, `POST /api/credentials/requests/{id}/fulfill` and `/cancel`, human sessions only), and the agent receives the AC_SECRET reference by calling the tool again. Requests are idempotent per scope and name, a declined request is not reopened by asking again, and each agent can have at most 20 open.
- Memory writes now report advisory warnings for likely active duplicates and matches to previously retracted records. Evidence-based confirmation is available through MCP, REST, and the dashboard.
- Memory consolidation can run on the configured maintenance interval, with an unconfirmed-inference rule, per-scope and installation-wide pending caps, a per-run budget, and fair rotation across rule/scope groups.
- Fresh MCP activity creation can return a bounded `since_last_active` workspace digest when its execution is not caught up. The Activity dashboard now shows execution-linked workspace activity rates for the installation lifetime and the last 30 days.
- Session context: `POST /api/session-context` and the MCP `session_context` tool return one budgeted block for session start: pinned rules, unfinished or handed-off work, recent results, changes since the agent's last session (one line per resource), and an index of key records. It replaces the startup `workspace_sync` plus searches, and opens the session's execution with its cursor at the newest change. The workspace is matched from the client's working directory against the configured workspace repo roots. Each injection is audited as `context_injected` with the record and activity ids it carried.
- Claude Code hook (`integrations/claude-code/agent_core_hook.py`, served at `/integrations/hooks/claude-code/agent_core_hook.py`). On SessionStart it injects the session context. On Stop, when the session's activity is open without a handoff, it blocks once and asks the agent to record one; it never asks twice for a task. It reads the URL and key from the existing MCP configuration and never breaks a session. The Integrations page has a **Claude Code Hook** output with install steps.
- Structured handoffs: `activity_update` (MCP) and `PUT /api/activity/{id}` accept `handoff` with `completed`, `next_steps`, `open_questions` and `needs_human`. The next session context shows next steps and open questions on recent work, and lists unresolved `needs_human` requests under "Waiting on a person" until they are resolved: by a person (`POST /api/activity/{id}/handoff/resolve`), by the agent that asked, or by a request that agent makes in a later session (see below). Closing an activity without a handoff returns a `HANDOFF_MISSING` warning. Migration 12 adds the handoff columns.
- Agents can settle their own handoff requests. A `needs_human` request recorded through `activity_update` or `PUT /api/activity/{id}` supersedes the agent's open requests in the same scope and for the same user that were made before the current activity started, so parallel sessions leave each other's requests alone. Superseding is per `metadata.task_ref`: tasks with different task_refs (such as separate jobs an orchestrator runs as one agent) never supersede each other, while terminal sessions without one supersede each other. The response lists them in `superseded_requests` (activity id, summary, `needs_human`, `open_questions`) so the agent can restate any that still apply, and each is audited as `handoff_superseded`. The new MCP tool `activity_handoff_resolve(activity_id, reason)` lets the agent an activity is assigned to resolve its request once dealt with. Closing a task without a request while earlier ones are open returns them in `open_requests` with an `OPEN_HANDOFF_REQUESTS` reminder and resolves nothing. A handoff for a completed or blocked task is added to its handoff rather than replacing it: new asks are appended as paragraphs of `needs_human`, list items are added, and no ask is removed except by a resolution. Over MCP, with no open task, a handoff alone goes to the agent's latest completed or blocked task in the scope, so a superseded request can be restated in the same session. `handoff_requested_at` now records when a request was made. Every resolution is stored in `handoff_json` as `resolution` (`kind` person, agent or superseded, `at`, `resolved_by`, `reason`, `superseded_by`); no migration. The Activity page keeps superseded requests visible in a collapsed group, and session context marks the calling agent's own open requests.
- Attention list for coordinators: the MCP `attention_list` tool and `GET /api/activity/attention` list unresolved `needs_human` requests across the scopes the caller reads, for an agent or dashboard that reports what is waiting on a person. It needs the `coordination` capability, not admin, and is read-only.
- `task_ref`: `activity_update`, `POST /api/activity` and `PUT /api/activity/{id}` accept `task_ref` (`<system>:<id>`, for example `jira:PROJ-123`), stored as `metadata.task_ref`, to link an activity to a task in another system. `attention_list` can skip requests that carry one (`without_task_ref`) when that system's own queue already lists them.
- Handoff events: activity webhook payloads include `handoff`, `handoff_resolved_at` and `task_ref`; every resolution sends `activity_handoff_resolved` with `handoff_resolution` (`person`, `agent` or `superseded`); and recording or resolving a handoff adds `handoff_recorded` or `handoff_resolved` to the workspace change feed.
- Workspace repository folder: admins link a workspace to a repository folder on the Edit Workspace dialog. Session context and the anchor verifier use it to pick the workspace from a session's working directory.
- Credential consumers: services and containers get their own resolve-only identity (`credentials_resolve`) and exact-entry grants, with optional versioned write-back for refreshed OAuth state. See [docs/credential-consumers.md](docs/credential-consumers.md). Nightly maintenance rolls successful resolution audits older than 30 days into daily counts.
- `memory_get(ids=[...])` fetches records by id, for the session-context index. Fetches are audited as `memory_fetched` and count as recalls.
- `result_fetch` reads are audited as `tool_result_fetched` against the offload handle. `scripts/value_report.py` reports whether stored data reaches agents: read-through of offloaded results, empty searches per agent, never-recalled memory per scope, and sync-stream composition.

## [1.0.0] - 2026-08-16

First stable release. Agent Core is a local capability layer for AI agents: shared memory, credentials, connectors, scoped access, activity tracking, and delegated authority in one SQLite-backed service.

### Memory

- Durable records in four classes (fact, decision, preference, scratchpad) with per-agent scoped access
- Facts carry subject anchors and are re-verified on a schedule; decisions are left alone by design
- Two independent timelines per record (transaction time and valid time), with `as_of` search for point-in-time questions
- Full-text search always; hybrid semantic search when an embedding backend such as Ollama is configured
- Ranking driven by observed recalls, caller feedback, and confirmation freshness rather than author self-assessment
- Pinned standing context, loaded at session start and capped per scope; agents request pins, operators grant them
- Clean-up rules that propose and never act; retraction is reversible

### Activity and handoffs

- Self-reported task trail with heartbeats, staleness detection, and a searchable history of what agents worked on
- Work assignment from the dashboard with explicit agent pickup, and generated briefings for handoffs
- Every memory write cites the activity that was open at the time, so a task links to what it concluded
- Per-execution `workspace_sync` cursors deliver pinned context, assignments, briefings, and workspace changes to each active session
- Durable change acknowledgements let two sessions with the same agent identity track their progress independently

### Credentials and connectors

- Fernet-encrypted credential store with key rotation and a keyring for old entries
- Agents receive `AC_SECRET_*` references, never raw values; a local broker resolves them at runtime
- Connector catalog built from OpenAPI imports, native MCP servers, shareable adapters, or generic HTTP
- Scoped bindings with connector-controlled actions, requirement gating, and deterministic resolution

### Delegated authorization

- Short-lived, narrowed grants: subset-only issuance, one-hour TTL cap, one-time REST-only claim, and replacement (never union) of the recipient's permanent authority
- Request and approval workflow with dashboard review; approval can keep or narrow permissions, never add them
- Lifecycle events on the live dashboard stream and outbound webhooks
- End-to-end attribution in the audit log; backups force live grants to revoked

### Operations

- Web dashboard with live SSE updates, audit log, and generated per-tool integration files
- Outbound signed webhook notifications and an inbound webhook receiver for external automation
- Backup and restore bundling the database with its key material; hourly maintenance sweep
- One REST API and 37 MCP tools over a shared service layer, in a single Docker container with all data on local disk
